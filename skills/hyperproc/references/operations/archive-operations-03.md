## Download lifecycle

Select a bounded subset. **Before downloading, disclose selected granules/assets, known reported volume plus unknown-size items, destination, free disk and unpack/work allowance; obtain approval for that concrete plan unless the session already explicitly authorizes this selection and transfer budget. Unknown sizes are not zero.** Use `scripts/download_plan.py` to prepare the report; it never downloads. `hp.download` writes provider assets plus required siblings, not necessarily one cube per granule. Identify primary file from actual names/metadata, then call the corresponding reader. Pair siblings using acquisition/datatake/time/tile identity; processing timestamps alone can incorrectly pair EnMAP products. Keep provider delivery structure unless a justified relocation preserves discovery.

DLR 0.1.2 stores `.part` files, resumes HTTP Range when supported, validates a 206 starting offset, overwrites on Range-ignored 200, handles known-complete 416, and retries selected transient errors with increasing waits. Progress resets the stall count. Persistent no-progress eventually raises; permission errors are not retried. Preserve partials for later attempts rather than writing an endless retry loop. Existing nonempty final files are reused, **not checksum verified**. Report transfer reuse accordingly. This behavior is specific to DLR, not every backend. Without a known total, size alone cannot prove completeness.
